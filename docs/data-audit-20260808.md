## (A) ランク分布の偏り

### 事象
顧客リストのテストデータ10行のうち、町域が確定した8件が全て **Sランク** で表示された。

### 原因（コード上の根拠）

**1. ランクの出所と結合は正しい（バグではない）。**
- 表示ランクは `public.town_monthly_metrics.inferred_priority_rank`。iwakuni（バックヤード正データ）から `priority_rank` として同期される値で、アプリ側で算出はしていない（同期関数 `public.sync_town_monthly_metrics_from_iwakuni` / `supabase/migrations/20260628000200_sync_iwakuni_town_monthly_metrics.sql:79`）。
- アタックリストは確定行の `town_name_normalized` を `(municipality_id, 正規化町名)` でランク表に join する（`src/app/api/customer-lists/[id]/attack-list/route.ts:92-98`、`src/lib/customer-list/server.ts:132-151`）。
- **本番DBで確定8行を実際に join した結果**：8件すべて岡崎市で、`明大寺町(S,acq48) / 稲熊町(S,50) / 羽根町(S,50) / 蓑川新町(S,50) / 大平町(S,50) / 戸崎町(S,49) / 土井町(S,49→実測48.x) / 藤川町(S,48)`。これらは岡崎市の**取得スコア上位10町域そのもの**。結合は 1:1 で正しく、住所解決も正確。

**2. つまり「8/8がS」は偶然ではなく、テスト住所が岡崎の急成長町域に集中していたため。**
- 全国最新 as_of のランク分布は **S=510 / A=648 / B=934 / C=1507 / D=5997**（Sは全体の5.3%）。岡崎単体でもS=33/356（9.3%）。ランクアルゴリズムは全体としてSに偏ってはいない。
- ランク閾値（取得スコア acq からの実測バンド）：`D: 0–10.9 / C: 11–17.9 / B: 18–27.9 / A: 28–39.9 / S: ≥40（実測40.0–70.0）`。

**3. ただし設計上の問題が2つある（ここが「算出式/閾値の問題」の実体）。**

- **(3-1) S帯が広く・飽和している。** Sは `acq≥40` の上限開放帯で、スコアが上限で頭打ちになっている：需要スコアは65、供給スコアは80で天井、取得スコアは離散値に集中（`50.0`に38件、`48.0`に20件、`47.0`に14件…）。結果、S帯内で町域を判別できない。「取得優先度の最上位を数件に絞る」用途に対し、S帯が広すぎる。
- **(3-2) アタックリストが取得スコアで副整列していない（アプリ層の欠落）。** `src/lib/customer-list/server.ts:46-47` の `SELECT_COLS` は `inferred_priority_rank` と `inferred_reason` のみを取得し、`inferred_acquisition_score` を**取得していない**。ソートは「ランク → 最終接触が古い順」だけ（`attack-list/route.ts:119-125`）。**全員がSだと副キーが last_contact しか無く、営業上の優先順位が付かない。**

**（参考・現時点は無害な潜在バグ）** `loadRankData` は同一正規化町名が複数 town_id に跨る場合、**最優先ランク（S>A>B>C>D）を採用**する（`server.ts:144-148`）。これはSへ引き上げるバイアスになりうる。本番実測では該当キー17件・ランク衝突9件・**Sへの昇格は0件**で、今回の8/8とは無関係。ただし将来データで顕在化しうる。

### 影響範囲（顧客に見える形）
- Platinum顧客がアタックリストを**優先順位付けに使えない**。今回のように顧客が成長エリアに集中していると全員Sになり、「どの顧客から攻めるべきか」の示唆がゼロになる。これはPlatinumの目玉機能の核心用途の機能不全。
- ランク自体が誤っているわけではない（表示は正しい）が、**識別力が無い**ため価値が出ない。

### 対応案

| 案 | 内容 | メリット | デメリット | 層 |
|---|---|---|---|---|
| **A（推奨・即効）** | `SELECT_COLS` に `inferred_acquisition_score` を追加し、アタックリストの同ランク内副ソート＆表示に使う | 低リスク・アプリ層のみ・全員Sでも順位が付く | 根本の閾値問題は残る | src/ のみ |
| B | ランク閾値の再設計（Sをさらに分割 / パーセンタイル化 / 自治体内相対ランク） | 「エリート少数」を表現できる | データ層(iwakuni)の算出見直しが必要・重い・全自治体再計算 | データ層 |
| C | 需要/供給の飽和上限を引き上げ、取得スコアの分解能を上げる | S帯内の判別が可能に | 同上・スコアの意味付け再定義が必要 | データ層 |

### 想定工数
- A案: **0.5〜1人日**（列追加＋副ソート＋テスト）。※本セッションでは未実装。
- B案: 3〜5人日（データ層のロジック改修＋全自治体再同期＋回帰）。
- C案: 2〜4人日（同上）。

### 緊急度
**中〜高。** データは「誤り」ではないので障害ではないが、Platinumの主機能が実質使えない。**A案は軽量なので3社オンボード前に入れる価値が大きい。** B/C（閾値再設計）はオンボード後で可。

## (B) 「売却0.0」が全町域で固定

### 事象
町域指標の「売却」値が、どの町域を見ても 0.0 で固定されている。

### 原因（コード上の根拠）

**1. 「売却」= `inferred_sell_signal_score`（＝iwakuni同期の推定スコア）。** 表示は `src/components/ui/TownPrioritySection.tsx:217` / `TownHighlightsPanel.tsx:229` の `売却 {fmtScore(t.inferred.sellSignalScore)}`。値は `/api/towns`（`src/app/api/towns/route.ts:116`）が `inferred_sell_signal_score` をそのまま返すもので、**不動産取引テーブルからは計算していない**。

**2. DB全体では「全件0.0」ではない。** 本番実測（最新as_of）：全町域のうち売却=0.0は約49%で、各自治体に最大 45〜67 の非0値が存在する（岩国67.2 / 姫路61.5 / 西宮61.6…）。よって「固定」ではなく、特定の見え方の問題。

**3. 売却スコアは成長と逆相関しており、成長町域では正しく≒0。** 本番実測（最新as_of・人口前年比で層別）：

| 人口トレンド | 町域数 | 売却 平均 | 売却=0の件数 | 需要 平均 |
|---|---|---|---|---|
| 減少(−) | 5,233 | **13.36** | 0 | 5.21 |
| 横ばい(0) | 1,044 | 3.61 | 821 | 3.85 |
| 成長(+) | 3,307 | **0.71** | 3,029 (92%) | 33.33 |

売却シグナル（＝売り物件が出やすさ）は**減少町域で高く・成長町域でほぼ0**という、ドメイン的に妥当な挙動。

**4. ダッシュボードは取得スコア降順（=成長・高需要町域）で上位表示するため、ユーザーは売却≒0の町域しか見ない（選択アーティファクト）。** `/api/towns` は `order('inferred_acquisition_score', desc)`（`route.ts:93`）、UIは上位10件のみ表示（`TownPrioritySection.tsx:10,107`）。本番実測：**各自治体の取得スコア上位10件（計220件）のうち203件（92%）が売却=0.0、平均0.89**。取得スコアは需要＋供給主導で売却をほぼ使わないため、上位＝成長町域＝売却≒0 になる。

**5. 桁数不一致（6桁 muni_code vs 5桁 city_code）は (B) の原因ではない。**
- アプリは入口で `toMuniCode6()`（`src/lib/muni-code.ts:39-45`）により**JIS X 0402の検査数字を付与して5→6桁化**してから `muni_code` で照合（`towns/route.ts:55`）。ゼロ埋めでなく検査数字（岩国35208→352080 等）で正しく変換済み。
- 不動産取引 `real_estate_transactions` は `municipality_id`（UUID）で結合（`src/hooks/useTransactions.ts:69`、投入も `fetch_realestate.py` が `city_code→id` で紐付け）。**コード桁での結合は行っていない。**
- そもそも売却スコアは `real_estate_transactions` から算出されず、iwakuni同期値をそのまま表示している。→ **桁ズレ仮説は棄却。**

### 影響範囲（顧客に見える形）
- 顧客は「売却スコアがいつも0＝壊れている」と誤解する。実際は「成長町域だから売却シグナルが低い」という正しい挙動だが、**UIにその文脈（＝なぜ0なのか）が無い**ため、製品の信頼性を損なうリスクがある。原則1（推定には根拠を伴わせる）の観点でも、0値に対する説明が弱い。

### 対応案

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| **A（推奨・軽量）** | 0.0時に `—` 表示や「成長期・売却シグナル低」等の注記を出す。reason（計算根拠）に売却が0である旨を明示 | 誤解を解消・低リスク・src/のみ | 根本の「見せ方」は上位表示のまま |
| B | 「売却上位（売り物件が出やすい町域）」を別軸/別タブで見せる。取得優先度とは別の営業導線 | 売却シグナルを死蔵しない・売主開拓に価値 | 中規模のUI追加 |
| C | 現状維持（仕様）だが、顧客に「取得優先度ビューでは売却が低いのが正常」と説明 | 工数0 | 誤解が残る・問い合わせ増 |

### 想定工数
- A案: **0.5人日**（表示・文言・reasonの補記）。※本セッションでは未実装。
- B案: 2〜3人日（別ビュー＋ソート＋テスト）。

### 緊急度
**中。** データは正しく障害ではない。ただし誤解を招くUIなので、**最低限の注記（A案）を3社オンボード前に入れるのが望ましい。** B案はオンボード後で可。

## その他の懸念（上記2件以外）

1. **アタックリストが `inferred_acquisition_score` を取得していない**（`server.ts:46-47`）。(A)の実害の核であり、単独でも改善価値が高い。
2. **同名異町域の「最優先ランク採用」バイアス**（`server.ts:144-148`）。現データではSへの昇格0件で無害だが、将来データで潜在的にランクを引き上げうる。副ソートに acquisition を入れる際に併せて設計を見直したい。
3. **自治体ごとに最新 as_of が異なる**（姫路/鹿児島=2026-03 〜 刈谷/安城/知立=2026-07）。アタックリストの突合基準月が顧客ごとに混在する。UIに自治体別 as_of 表示はあるが（`as_of_by_municipality`）、鮮度差は顧客説明が必要。
4. **スコア飽和**（需要65・供給80の頭打ち、取得スコアの離散的集中）。S帯の分解能を根本的に下げており、(A)のB/C案の背景。データ層での是正が本筋。
5. 監査時点で `town_monthly_metrics` は全期間194,201行・最新as_ofのみで9,596件。RLS（platinum限定SELECT）・plan gatingは設計どおりで、今回の2件とは無関係。

## 検証に使用した読み取り専用クエリ（再現用）

- ランク分布（最新as_of）: `inferred_priority_rank` を GROUP BY → S=510/A=648/B=934/C=1507/D=5997
- 閾値バンド: rank 別 `min/max(inferred_acquisition_score)` → S≥40 の開放帯を確認
- 売却の成長逆相関: `confirmed_population_yoy_delta` の符号で層別した `avg(inferred_sell_signal_score)`
- 上位10町域の売却: 自治体別 `row_number() OVER (ORDER BY acquisition DESC)` ≤10 で 92% がsell=0
- 確定8行の実ランク: `customer_list_rows`（confirmed）× `customer_list_town_latest` 相当の join
- 桁数処理: `src/lib/muni-code.ts` の検査数字ロジックと `towns/route.ts` の入口正規化を読解

> ※ 本レポート作成にあたり、本番DBへの書き込み・DDL・マイグレーション適用は一切行っていない。アプリコードも1行も変更していない。
